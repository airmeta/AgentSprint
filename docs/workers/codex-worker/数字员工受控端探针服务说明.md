# 数字员工受控端探针服务说明

## 定位

`AgentSprint.Worker` 是数字员工受控端的第一阶段控制台宿主，基于 `Air.Cloud.HostApp` 启动，不提供 HTTP API。它用于承载一个 Codex 数字员工实例，并在后续阶段接入 AgentSprint 主平台的注册、心跳、命令和任务领取闭环。

## 启动入口

项目路径：

```text
src/api/AgentSprint.Worker/
```

入口使用 HostApp 注入：

```csharp
var hostBuilder = Host.CreateDefaultBuilder(args);
hostBuilder.HostInjectInFile(Assembly.GetExecutingAssembly());
```

该入口只使用 `Air.Cloud.HostApp`，不混用 `Air.Cloud.WebApp`，避免同一入口项目出现多个 `IAppInjectStandard` 实现。

## 当前能力

- 读取 `Worker` 和 `AgentSprint` 配置段。
- 检查并创建 `WorkspaceRoot` 和 `RunsRoot`。
- 检查 `CodexHome/config.toml` 是否存在。
- 执行环境探针：
  - `codex --version`
  - `git --version`
  - `dotnet --version`
  - `node --version`
  - `codex login status`
- 可通过 `Worker:RunSmokeOnStartup=true` 启动一次 `codex exec` smoke run。
- 每次 run 落盘：
  - `prompt.txt`
  - `stdout.log`
  - `stderr.log`
  - `final.md`
  - `run.json`

## Standalone Deployment Contract

`AgentSprint.Worker` should be deployed as a generic controlled endpoint. The container only needs two platform identity settings:

```yaml
environment:
  AgentSprint__ApiBaseUrl: "http://api:5000"
  AgentSprint__AgentToken: "${AGENTSPRINT_AGENT_TOKEN}"
```

`WorkerId`, `WorkerName`, workspace paths, run-log paths, `CodexHome`, MCP endpoint, polling cadence, max run minutes, sandbox mode, smoke policy, Codex provider/model/base URL, and similar runtime settings come from the `digital_worker` management record. On startup the Worker calls `GET /worker-runtime/config` with the Agent Token in `Authorization: Bearer ...`; the platform validates `sys_agent_token`, finds the bound `digital_worker.AgentTokenId`, and returns the full runtime config.

Each digital worker still needs its own container, Agent Token, and mounted directories. Mounts are container resources, so compose or the container platform still declares them, while worker identity and runtime behavior stay in digital-worker management.

## Prompt Runtime Context

The platform prepends a non-secret digital-worker runtime context to every work prompt returned by `GET /worker-runtime/work/{targetType}/{targetId}/prompt`. The context includes worker identity, workspace root, resolved project workspace path, runs/log root, `CodexHome`, sandbox mode, Codex provider/model, polling limits, concurrency limits, config version, bound project IDs, endpoint IDs, skill IDs, and worker description.

Before `AgentSprint.Worker` calls `codex exec`, it also prepends the current run context to the actual prompt written to `prompt.txt`. That section includes the run ID, working directory, run directory, `prompt.txt`, `stdout.log`, `stderr.log`, `final.md`, `run.json`, Codex Home, sandbox mode, model, timeout settings, and prepared Git branch/commit state.

Sensitive values are intentionally excluded from both prompt layers. Agent Token values, Git access tokens, API keys, database passwords, and SSH private keys must stay in Worker process memory or Codex auth/config files and must not be rendered into the prompt.

## Codex Silence And Gateway Diagnostics

`AgentSprint.Worker` starts `codex exec` as a child process and continuously pumps its `stdout` and `stderr` into the run directory. The idle timeout is based on those two streams, not on direct visibility into the Codex CLI internal HTTP client. If Codex starts but the model gateway never sends a response stream, or the CLI waits before emitting its first line, the Worker may see a running process with no output.

To make that state visible on the platform, the Worker reports progress events while the process is still alive:

- `codex_idle_waiting`: emitted once after half of `Worker:CodexIdleTimeoutSeconds` passes without recent `stdout` or `stderr`.
- `codex_idle_timeout`: emitted immediately before the Worker marks the run as `timeout` because the full idle timeout elapsed.

Both events include `localRunId`, `observedAt`, `lastOutputAt`, `idleForSeconds`, `idleTimeoutSeconds`, and `hasOutput` in `payloadJson`. When `hasOutput=false`, the run has not produced any Codex CLI output since launch, so compare `observedAt` and the run start time with the AI gateway access logs to determine whether the CLI sent a request at all.

The Worker also writes a local `Codex启动环境诊断` log immediately before `Process.Start()`. The line includes the effective `CODEX_HOME`, `config.toml` existence, length, last-write timestamp, short SHA-256 fingerprint, configured `model`, `model_provider`, `base_url`, timeout values, and whether key environment variables such as `OPENAI_API_KEY` and proxy settings are present. Secret values are never printed; only boolean presence flags and non-secret configuration metadata are logged.

## Worker Git Workspace Preparation

Before a `start_task` or `start_bug` command enters `codex exec`, `AgentSprint.Worker` prepares the project workspace with `GitWorkspaceManager`.

Flow:

1. Worker reads `projectCode`, `repositoryUrl` and optional `branch` from the command payload or from `GET /worker-runtime/work/{targetType}/{targetId}/prompt`.
2. Worker resolves the local path as `{WorkspaceRoot}/{projectCode}`.
3. If the directory is missing or empty, Worker runs `git clone`.
4. If the directory already contains `.git`, Worker runs `git remote set-url origin` when needed, then `git fetch --prune origin`, branch checkout, and `git pull --ff-only`.
5. Worker reports `workspace_prepared` with `workspacePath`, `repositoryAvailable`, `branch`, `commit` and `dirty`.
6. Only after the workspace is ready does Worker start `codex exec`; real task and bug runs no longer use `--skip-git-repo-check`.

If the project has no repository URL, Worker creates the workspace directory but marks the run as `blocked` before starting Codex. This keeps real development tasks from running in an empty folder.

After a successful task or bug run, Worker now publishes code changes before marking the target complete:

1. If the prepared workspace is already dirty before Codex starts, Worker blocks the run to avoid mixing stale local edits into the new task.
2. After Codex succeeds, Worker checks `git status --porcelain`. If no files changed, no commit or push is created.
3. If files changed, Worker stages all task changes, creates one local task commit, runs `git fetch --prune origin`, merges `origin/{currentBranch}`, and pushes the current branch.
4. If the merge conflicts, Worker starts a follow-up Codex conflict-resolution run. The conflict prompt requires Codex to remove conflict markers, preserve both local and remote intent, and keep any discarded side as a nearby code comment instead of deleting it outright.
5. Worker, not Codex, performs the final `git add`, merge commit, and `git push origin {currentBranch}`. If publish fails, the platform run is marked `blocked` and the task/bug completion API is not called.
6. Worker reports `workspace_published` with `workspacePath`, `hasChanges`, `pushed`, `conflictResolved`, `branch`, `commit`, and `error`.

Security boundary:

- `repositoryReference` remains the sanitized value used in prompt text.
- `repositoryUrl` is returned in the prompt context for Worker only and is used directly by the Git tool.
- Worker does not write the real repository URL into `prompt.txt` or ask Codex to run the initial clone/fetch/pull step.

## Worker Command Audit And Replay

The management API exposes the full `worker_command` audit stream through `GET /workers/commands`. Admin pages can filter by `workerId`, `sessionId`, `commandType`, and `status`; `workerId` accepts either the digital-worker ID or code.

The digital-worker management page uses a single-select table checkbox to choose the current worker. The toolbar `命令审计` action opens the command audit drawer for that worker, lists all matching commands, and supports replaying a historical command.

Replay calls `POST /workers/commands/{commandId}/replay`. The platform copies the source command type and payload into a new `pending` command for the same worker. It does not copy the previous session, ACK/start/completion timestamps, result, or error, so the controlled Worker receives the replay through the normal heartbeat command loop.

## Worker Command Log Streaming

`AgentSprint.Worker` now streams command output to the platform while a command is still running. The Worker batches stdout/stderr text every 200 ms and first sends each chunk through the platform Akka actor `agentsprint-platform-worker-command-log-receiver`. If Akka delivery throws locally, the Worker falls back to `POST /worker-runtime/command-logs/append` so command-log collection still works during Akka rollout or partial outages.

The platform receiver writes each chunk through `IDigitalWorkerRuntimeService.AppendCommandLogAsync`. The live snapshot is stored in Redis through `Air.Cloud.Modules.RedisCache` and the management API/SSE endpoints read the same snapshot for task monitoring:

- `GET /workers/commands/{commandId}/log`
- `GET /workers/commands/{commandId}/log/stream`

When the Worker sends a completion marker, the platform archives the accumulated text into `worker_command_log`, clears the Redis live snapshot, and keeps only the latest 200 database log records for the same Worker instance.

Required platform configuration:

```json
{
  "RedisSettings": {
    "ConnectionString": "192.168.80.101:6379",
    "UserName": "",
    "Password": ""
  },
  "AkkaSettings": {
    "SystemName": "agentsprint-cluster",
    "Host": "api",
    "Port": 25520,
    "SeedNodes": [ "akka.tcp://agentsprint-cluster@api:25520" ],
    "Roles": [ "agentsprint-platform" ],
    "Domains": {
      "AgentSprintPlatform": {
        "Role": "agentsprint-platform",
        "ActorNamePrefix": "agentsprint-platform",
        "AllowCrossDomainMessages": true
      }
    }
  }
}
```

When Worker command-log Akka delivery reports `Akka actor 'agentsprint-platform-worker-command-log-receiver' has not registered`, first verify the API and Worker are in the same Akka cluster. The API container should expose the seed node, and Worker containers should use the same `AkkaSettings:SystemName` plus the API seed node:

```yaml
AkkaSettings__SystemName: "agentsprint-cluster"
AkkaSettings__SeedNodes__0: "akka.tcp://agentsprint-cluster@api:25520"
```

Use a routable container DNS name for `AkkaSettings__Host`: `api` on the API container and the Worker container name, for example `math-codex-worker-1`, on that Worker container.

The API keeps the `agentsprint-platform` role and registers `agentsprint-platform-worker-command-log-receiver`; Workers keep the `agentsprint-worker` role and only send to that platform actor. If the ActorSystem names differ, no seed node is configured, or `AkkaSettings:Host` is left as `0.0.0.0`, each process can start an isolated or unreachable cluster node and the Worker cannot discover the platform receiver even though both processes are running. In healthy logs, node addresses should use the shared system name and routable container DNS names, for example `akka.tcp://agentsprint-cluster@api:25520` and `akka.tcp://agentsprint-cluster@math-codex-worker-1:<port>`.
