# 代码审计功能排程

## 目标

代码审计功能用于在 AgentSprint 中发布只读审计任务，由数字员工拉取最新代码后，基于指定代码范围、任务变更、需求模块或文字性功能点进行代码审计，并沉淀结构化审计结果。

该功能只看代码、只研究代码、只输出审计结论，不修改代码、不生成补丁、不提交代码、不推进开发任务状态。

## 核心场景

1. 按任务大厅任务 ID 审计。
   - 需求拆解后会产生多个开发任务。
   - 数字员工推进任务后会留下 Git 变更记录。
   - 发布审计任务时可选择某个开发任务 ID，系统审计该任务实际产生的 Git 变更。

2. 按代码范围审计。
   - 支持选择一个代码范围。
   - 支持选择 N 个代码文件夹。
   - 支持选择 N 个代码文件。

3. 按业务范围审计。
   - 支持选择某个需求模块。
   - 支持输入某个文字性描述的功能点。

4. 按发布前检查审计。
   - 可在发布前选择多个任务、模块或文件范围。
   - 数字员工统一拉取最新代码并输出审计结果。

## 审计原则

1. 代码审计不做任何代码调整。
2. 审计 Worker 不调用任务完成接口，不改变开发任务、需求或缺陷状态。
3. 审计前必须拉取最新代码。
4. 审计结果必须能关联到项目、仓库、分支、审计范围、数字员工、命令、运行记录。
5. 审计必须结合 Skill，包括项目规范、框架规范、注释规范、安全规范和验证规范。
6. 注释检查必须精确到类、方法、方法参数级别。
7. 审计完成后必须维护文件级审计状态，用于后续统计仓库审计覆盖率和单独发起未审计文件审计。

## 提示词模板

新增提示词模板：

- `AgentEnvironment`: `codex`
- `Code`: `code_audit`
- `Name`: `代码审计提示词`

模板变量：

- `{{auditTargetType}}`
- `{{taskId}}`
- `{{requirementId}}`
- `{{moduleId}}`
- `{{scope}}`
- `{{repository}}`
- `{{branch}}`
- `{{changedFiles}}`
- `{{diff}}`
- `{{codeContext}}`
- `{{skillContext}}`
- `{{instruction}}`

Skill 上下文需要由后端或 Worker 构建后注入 `{{skillContext}}`，不能只在提示词中声明变量。

## Skill 传递规则

审计任务需要根据审计范围合并 Skill：

1. 任务 ID 审计。
   - `SprintRequirement.SkillIds`
   - 审计 Worker 的 `DigitalWorker.SkillIds`
   - 发布审计任务时手动选择的 SkillIds

2. 需求模块审计。
   - 项目 SkillIds
   - 端或模块 SkillIds
   - 审计 Worker SkillIds
   - 手动选择的 SkillIds

3. 文件、文件夹、文字功能点审计。
   - 项目 SkillIds
   - 审计 Worker SkillIds
   - 手动选择的 SkillIds

合并后按 Skill Code 排序，去重，只取启用状态的 Skill。

## 数据模型排程

### 第 1 阶段：审计任务主表

- `Id`
- `ProjectId`
- `GitRepositoryId`
- `Branch`
- `WorkerId`
- `AuditTargetType`
- `TargetId`
- `SourceTaskId`
- `SourceCommandId`
- `SourceRunId`
- `SourceGitCommitId`
- `BaseCommitId`
- `HeadCommitId`
- `CurrentBranchHeadCommitId`
- `RequirementId`
- `ModuleId`
- `ScopeJson`
- `SelectedSkillIds`
- `Instruction`
- `Status`
- `Conclusion`
- `WorkspaceDirtyReason`
- `CreatedBy`
- `StartedAt`
- `CompletedAt`
- `CreateTime`
- `UpdateTime`
- `IsDelete`

建议状态：

- `pending`
- `running`
- `passed`
- `needs_changes`
- `blocked`
- `failed`
- `cancelled`

关键字段约束：

- `Branch` 保存本次审计实际使用的分支，不能只依赖仓库默认分支。
- `SourceTaskId`、`SourceCommandId`、`SourceRunId`、`SourceGitCommitId` 用于固化任务 ID 审计的来源链路，第一期即落库，避免后续只靠动态关联 `worker_run` 造成历史审计不可追溯。
- `BaseCommitId`、`HeadCommitId` 保存本次审计 diff 的版本边界。
- `CurrentBranchHeadCommitId` 保存审计开始时远端或本地拉取后的分支最新提交，用于判断审计目标是否落后于当前分支。
- `WorkspaceDirtyReason` 记录审计后工作区出现新增、修改或删除时的异常原因；只读审计不应产生任何仓库变更。

### 第 2 阶段：审计结果表

新增 `code_audit_result`：

- `Id`
- `AuditTaskId`
- `WorkerCommandId`
- `WorkerRunId`
- `GitCommitId`
- `Branch`
- `ChangedFilesJson`
- `PromptSnapshot`
- `SkillContextSnapshot`
- `RawResult`
- `StructuredResultJson`
- `Conclusion`
- `IssuesJson`
- `AnnotationIssuesJson`
- `ManualCheckItemsJson`
- `CreateTime`
- `UpdateTime`
- `IsDelete`

结果表保存提示词快照和 Skill 快照，避免后续模板或 Skill 改动后无法还原当时审计依据。

`RawResult` 保存 Worker/Codex 原始输出，`StructuredResultJson` 保存后端解析后的完整结构化结果。`IssuesJson`、`AnnotationIssuesJson`、`ManualCheckItemsJson` 从 `StructuredResultJson` 拆分生成，不能只依赖 Markdown 文本临时解析。

### 第 3 阶段：文件级审计状态表

新增 `code_audit_file`，作为审计结果要求的一部分，用于维护项目内每个代码文件当前的审计状态。

字段建议：

- `Id`
- `ProjectId`
- `GitRepositoryId`
- `Branch`
- `FileType`
- `FilePath`
- `FilePathHash`
- `FileContentHash`
- `AuditStatus`
- `LastAuditTaskId`
- `LastAuditResultId`
- `LastAuditAt`
- `LastCommitId`
- `IssueCount`
- `BlockingIssueCount`
- `HighIssueCount`
- `MediumIssueCount`
- `LowIssueCount`
- `Summary`
- `CreateTime`
- `UpdateTime`
- `IsDelete`

`AuditStatus` 建议值：

- `normal`
- `abnormal`
- `not_audited`

索引建议：

- 唯一索引：`ProjectId + GitRepositoryId + Branch + FilePathHash`
- 普通索引：`ProjectId + AuditStatus`
- 普通索引：`ProjectId + FileType`
- 普通索引：`GitRepositoryId + Branch`
- 普通索引：`LastAuditAt`

路径和 Hash 规则：

- `FilePath` 使用仓库相对路径。
- 路径分隔符统一为 `/`。
- `FilePathHash` 用标准化后的文件路径计算。
- `FileContentHash` 用文件内容计算，用于判断文件内容变化后是否需要重新审计。
- `FileType` 按文件后缀识别，例如 `js`、`css`、`cs`、`java`、`ts`、`vue`。

维护规则：

1. 审计任务完成后，根据本次审计涉及的文件列表逐个 upsert。
2. 根据 `FilePathHash` 判断更新或新增。
3. 文件无明确问题时，`AuditStatus = normal`。
4. 文件存在明确问题时，`AuditStatus = abnormal`。
5. 新发现但未审计的文件，`AuditStatus = not_audited`。
6. 如果文件内容变化，后续 Git 同步阶段可以根据 `FileContentHash` 将状态重置为 `not_audited`。

第一期代码审计闭环中，先由审计任务结果回写 `code_audit_file`。Git 仓库定期索引和全仓库文件同步后续再加。

## 后端接口排程

### 第 1 阶段：发布审计任务

新增接口：

- `POST /api/code-audit/tasks`

请求字段：

- `projectId`
- `workerId`
- `auditTargetType`
- `targetId`
- `scope`
- `selectedSkillIds`
- `instruction`

`auditTargetType` 建议值：

- `development_task`
- `files`
- `folders`
- `requirement_module`
- `feature_description`

发布接口事务边界：

1. 校验项目、仓库、分支、Worker、审计范围和 Skill。
2. 创建 `code_audit_task`，状态为 `pending`。
3. 创建 `worker_command`，`CommandType = code_audit`，Payload 只包含 `auditTaskId` 和必要的幂等键。
4. 任务和命令必须在同一事务中提交；命令创建失败时不得留下不可调度的审计任务。
5. Worker 禁用、无项目权限、无可用仓库或审计范围非法时，直接拒绝发布，不创建任务。
6. Worker 离线但允许排队时，任务保持 `pending`；不允许排队时，任务创建前返回错误。

### 第 2 阶段：查询审计任务

新增接口：

- `GET /api/code-audit/tasks`
- `GET /api/code-audit/tasks/{id}`
- `GET /api/code-audit/tasks/{id}/result`

### 第 3 阶段：取消和重试

新增接口：

- `POST /api/code-audit/tasks/{id}/cancel`
- `POST /api/code-audit/tasks/{id}/retry`

取消只影响未开始或正在排队的任务。已经进入 Worker 执行的任务先标记取消意图，实际中断能力后续再做。

## 审计范围解析排程

### 任务 ID 审计

输入 `development_task` + `taskId` 后：

1. 查 `SprintDevelopmentTask`。
2. 查关联 `SprintRequirement`。
3. 查项目和 Git 仓库。
4. 查该任务最近一次相关 Worker Run 或 Worker Command。
5. 固化 `SourceTaskId`、`SourceCommandId`、`SourceRunId`、`SourceGitCommitId`。
6. 优先使用 `SourceGitCommitId` 生成 diff。
7. 如果能找到父提交，保存 `BaseCommitId = parent(SourceGitCommitId)`、`HeadCommitId = SourceGitCommitId`。
8. 拉取最新分支后保存 `CurrentBranchHeadCommitId`。
9. 如果 `HeadCommitId` 不是当前分支可达提交，或审计目标明显落后于当前分支，需要将该风险写入审计上下文。
10. 没有 `SourceGitCommitId` 时使用 `ChangedFilesJson` 和工作区 diff，但必须把版本边界不完整列为人工确认项。
11. 生成 `changedFiles`、`diff`、`codeContext`。

需要注意：当前 `worker_command` 本身不直接存 `taskId`，需要通过 `worker_run.CommandId + TargetType + TargetId` 关联。第一期必须在审计任务里保存 `SourceTaskId`、`SourceCommandId`、`SourceRunId`，降低查询复杂度并保证历史审计可追溯。

### 文件或文件夹审计

输入文件路径或文件夹路径后：

1. 校验路径必须位于项目工作区内。
2. 拉取最新代码。
3. 收集目标文件内容。
4. 对文件夹设置文件数量和总字符数上限。
5. 生成 `codeContext`。

### 需求模块审计

输入模块 ID 后：

1. 查模块所属项目、端和仓库。
2. 根据模块配置或约定路径定位代码范围。
3. 如果模块没有代码路径，需要允许用户补充路径或功能描述。
4. 合并模块、项目、Worker 和手选 Skill。

### 文字功能点审计

输入功能点描述后：

1. 拉取最新代码。
2. 先由 Worker 定位可能相关文件。
3. 生成候选文件清单。
4. 审计候选文件与功能点描述是否一致。

该模式需要限制扫描范围，避免全仓库无界读取。

## Worker 执行排程

### 第 1 阶段：命令类型

新增 Worker 命令类型：

- `code_audit`

命令 Payload：

- `auditTaskId`

Worker 收到命令后：

1. Ack command。
2. Start run，`RunType = code_audit`。
3. 获取审计任务详情和审计提示词。
4. 准备 Git 工作区。
5. 执行只读审计。
6. Finish run。
7. 回写审计结果。

### 第 2 阶段：Git 工作区准备

复用 `GitWorkspaceManager`：

- clone
- fetch
- checkout
- pull --ff-only
- status

如果拉取失败，审计任务状态为 `blocked`。

### 第 3 阶段：只读约束

Worker 代码审计模式要求：

1. 不调用 `CompleteWorkAsync`。
2. 不执行提交。
3. 不推送。
4. 不把审计产生的文件变更作为业务结果。
5. 如工作区在审计后出现新增变更，需要标记为异常。

第一期验收标准：

1. 审计执行前记录 `git status --porcelain`。
2. 审计执行后再次检查 `git status --porcelain`。
3. 如果审计前工作区不干净，任务状态置为 `blocked`，并写入 `WorkspaceDirtyReason`。
4. 如果审计后出现新的工作区变更，任务状态置为 `failed` 或 `blocked`，并写入 `WorkspaceDirtyReason`。
5. `code_audit` 命令分支必须跳过 `PublishAsync`、`CompleteWorkAsync` 和任何提交/推送逻辑。

后续可以把审计 Worker 的 sandbox 调整为只读模式；第一阶段至少在命令分支中避免完成任务和提交逻辑，并通过工作区前后状态校验兜底。

## 分阶段交付

### P0：提示词和数据入口

- 完成 `code_audit` 提示词模板。
- 初始化 SQL 和单独 seed SQL 保持一致。
- 代码审计任务页保留占位说明。

### P1a：任务 ID 审计数据入口

- 新增审计任务表和结果表。
- 新增文件级审计状态表，并在审计完成后按文件路径 Hash 回写状态。
- 审计任务表一期包含 `SourceTaskId`、`SourceCommandId`、`SourceRunId`、`SourceGitCommitId`、`BaseCommitId`、`HeadCommitId`、`CurrentBranchHeadCommitId`。
- 支持按任务 ID 发布审计任务。
- 发布接口创建审计任务和 `code_audit` Worker 命令必须在同一事务内完成。

### P1b：Worker 只读审计执行

- 新增 Worker 命令类型 `code_audit` 和运行类型 `code_audit`。
- Worker 拉取最新代码。
- 基于任务关联的 Git 变更审计。
- `code_audit` 分支跳过 `PublishAsync`、`CompleteWorkAsync`、提交和推送逻辑。
- 审计前后检查工作区状态，出现脏工作区时写入 `WorkspaceDirtyReason` 并阻断或失败。
- 审计输出必须包含固定结构化 JSON，Markdown 只作为展示文本。

### P1c：结果回写和管理端展示

- 回写结果并在管理端展示。
- 保存 `RawResult`、`StructuredResultJson`、提示词快照和 Skill 快照。
- 从 `StructuredResultJson` 拆分写入问题列表、注释问题和人工确认项。
- 按文件路径 Hash 和内容 Hash 回写 `code_audit_file`。
- 管理端任务页、结果页接入真实接口，并提供 Worker 命令日志入口。

### P2：文件和文件夹审计

- 基于 `code_audit_file` 支持筛选未审计、异常、正常文件。
- 支持 N 个文件。
- 支持 N 个文件夹。
- 支持代码上下文大小限制。
- 支持 Skill 多选。

### P3：模块和功能点审计

- 支持需求模块审计。
- 支持文字功能点描述审计。
- 支持候选文件定位。

### P4：发布审计

- 支持多个任务或多个范围合并审计。
- 支持发布前统一审计报告。
- 支持导出审计报告。

### P5：Git 仓库索引同步

- 定期同步仓库代码文件清单。
- 根据项目、分支、文件路径 Hash 维护 `code_audit_file`。
- 新增文件标记为 `not_audited`。
- 内容变化文件标记为 `not_audited`。
- 已删除文件软删除或标记为删除状态。
- 支持按未审计文件批量发布审计任务。

## 风险和约束

1. 任务变更关联关系需要明确。
   - 当前应通过 Worker Run 的 `TargetType` 和 `TargetId` 找任务。
   - 后续建议在审计任务中保存来源命令和来源运行。

2. 只读约束需要代码层保证。
   - 不能只依赖提示词约束。
   - Worker 的 `code_audit` 分支必须跳过完成任务、提交、推送逻辑。

3. 大范围审计需要限制上下文大小。
   - 文件数量、总字符数、单文件大小都需要限制。
   - 超限时要求用户缩小范围。

4. Skill 必须保存快照。
   - 审计结果需要保留当时使用的 Skill 内容。
   - 否则后续 Skill 被修改后无法解释历史审计结论。

5. 文件级状态不能只依赖路径。
   - `FilePathHash` 用于定位文件。
   - `FileContentHash` 用于判断文件内容是否变化。
   - 后续 Git 索引同步时，内容变化应使文件重新进入未审计状态。

6. 注释检查容易泛化。
   - 提示词已经要求精确到类、方法、参数。
   - 实现侧应尽量提供代码结构上下文，而不仅是 diff。

## 建议优先实现

第一轮只做任务 ID 审计闭环：

1. 发布审计任务。
2. 创建 `code_audit_task` 和 `worker_command(code_audit)`。
3. 根据任务 ID 找最近一次 Worker 变更，并固化来源命令、来源运行和提交边界。
4. 拉取最新代码并记录当前分支 HEAD。
5. 注入 Skill 快照。
6. 调用 `code_audit` 只读执行分支。
7. 校验审计前后工作区状态，确认未产生提交、推送或业务状态变更。
8. 保存原始输出和结构化审计结果。
9. 按文件路径 Hash 和内容 Hash 回写 `code_audit_file`。
10. 管理端展示任务、结果和 Worker 命令日志。

这个闭环跑通后，再扩展文件、文件夹、模块和功能点审计。
