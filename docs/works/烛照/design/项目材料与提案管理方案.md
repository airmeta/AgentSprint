# 项目材料与提案管理方案

## 1. 设计目标

项目材料功能先作为项目管理的子能力落地，形成一个按项目隔离的文件管理区。后续提案管理基于这些材料做 AI 对话和提案生成，再把确认后的提案转换为需求，接入现有敏捷研发闭环。

设计原则：

- 项目是材料、提案和需求的共同边界。
- 第一版文件保存在 API 运行目录，但数据模型必须保留存储根和相对路径，方便后续迁移对象存储。
- 原始文件、抽取文本、AI 生成内容和最终需求之间必须可追溯。
- 提案转需求不能绕过需求评审和任务拆解。
- 管理端页面遵循现有项目上下文和列表页交互规范。

## 2. 当前系统衔接点

现有敏捷研发模块已经具备：

- `SprintProject`：项目管理。
- `SprintRequirement`：需求管理。
- `SprintDevelopmentTask`：任务大厅和我的任务。
- `SprintBug`：缺陷管理。
- `SprintRequirementFeedback`：需求回馈转后续需求。
- `ProjectMember`：参与项目范围和权限判断。
- MCP 和数字员工上下文：用于后续 AI 或 Worker 协作。

本方案新增：

- `SprintProjectMaterial`：项目材料和文件夹。
- `SprintProjectMaterialEvent`：材料审计事件。
- `SprintProposal`：提案。
- `SprintProposalMaterial`：提案与材料关系。
- `SprintProposalConversation`：提案 AI 对话记录。
- `SprintProposalRequirement`：提案转需求关系。

## 3. 数据模型设计

### 3.1 SprintProjectMaterial

用于保存项目材料文件和逻辑文件夹。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `Id` | string | 材料 ID。 |
| `ProjectId` | string | 所属项目。 |
| `ParentId` | string? | 上级文件夹。 |
| `ItemType` | string | `file` / `folder`。 |
| `Name` | string | 展示名称。 |
| `OriginalFileName` | string? | 上传原文件名。 |
| `Extension` | string? | 扩展名。 |
| `ContentType` | string? | MIME 类型。 |
| `SizeBytes` | long | 文件大小。 |
| `StorageRoot` | string | 第一版为 `api_run_directory`。 |
| `RelativePath` | string? | 相对 API 运行目录的物理路径。 |
| `Sha256` | string? | 文件哈希。 |
| `Category` | string? | 分类。 |
| `TagsJson` | text? | 标签 JSON。 |
| `Description` | text? | 说明。 |
| `ExtractStatus` | string | `none` / `pending` / `completed` / `failed` / `unsupported`。 |
| `ExtractedTextPath` | string? | 抽取文本相对路径。 |
| `Summary` | text? | 摘要。 |
| `UploadedBy` | string | 上传人。 |
| `CreatedAt` | datetime | 创建时间。 |
| `UpdatedAt` | datetime | 更新时间。 |
| `DeletedAt` | datetime? | 软删除时间。 |

索引建议：

- `(ProjectId, ParentId, DeletedAt)`
- `(ProjectId, ItemType)`
- `(ProjectId, UploadedBy)`
- `(ProjectId, CreatedAt)`
- `(Sha256)`

约束建议：

- `ItemType=folder` 时 `RelativePath` 为空。
- `ItemType=file` 时 `RelativePath` 必填。
- 同一项目下 `ParentId` 必须指向同项目文件夹。

## 4. 文件存储设计

### 4.1 配置项

建议新增配置：

```json
{
  "ProjectMaterials": {
    "StorageRoot": "api_run_directory",
    "RelativeRootPath": "project-materials",
    "MaxFileSizeMb": 50,
    "AllowedExtensions": [".md", ".txt", ".pdf", ".docx", ".xlsx", ".pptx", ".png", ".jpg", ".jpeg", ".zip"]
  }
}
```

第一版路径解析：

```text
root = Path.Combine(AppContext.BaseDirectory, RelativeRootPath)
projectRoot = Path.Combine(root, projectId)
filePath = Path.Combine(projectRoot, "files", yyyy, MM, materialId + extension)
```

所有路径写入前必须：

- 使用 `Path.GetFullPath` 归一化。
- 校验目标路径以项目根目录开头。
- 使用服务端生成的文件名。

### 4.2 Docker 和部署约束

如果 API 跑在容器中，需要在 compose 中挂载：

```text
/app/project-materials
```

发布脚本不能删除这个目录。后续迁移对象存储时可以保留数据库记录，并通过迁移任务把 `StorageRoot` 从 `api_run_directory` 改为 `object_storage`。

## 5. 后端服务设计

### 5.1 Controller

建议新增控制器：

```text
ProjectMaterialController
ProposalController
```

也可以为了延续 MVP 路径风格，把接口挂在 `AgileMvpController` 下，但当材料和提案接口增多后，独立控制器更清晰。

建议路由：

```text
GET    /mvp/projects/{projectId}/materials
POST   /mvp/projects/{projectId}/materials/folders
POST   /mvp/projects/{projectId}/materials/upload
GET    /mvp/materials/{materialId}
GET    /mvp/materials/{materialId}/download
PUT    /mvp/materials/{materialId}
PUT    /mvp/materials/{materialId}/move
DELETE /mvp/materials/{materialId}

GET    /mvp/projects/{projectId}/proposals
POST   /mvp/projects/{projectId}/proposals
GET    /mvp/proposals/{proposalId}
PUT    /mvp/proposals/{proposalId}
POST   /mvp/proposals/{proposalId}/generate
POST   /mvp/proposals/{proposalId}/confirm
POST   /mvp/proposals/{proposalId}/convert-to-requirements
```

### 5.2 Service

建议新增服务接口：

```text
IProjectMaterialService
IProposalService
```

`IProjectMaterialService` 能力：

- `ListMaterialsAsync`
- `CreateFolderAsync`
- `UploadAsync`
- `GetMaterialAsync`
- `OpenDownloadAsync`
- `RenameAsync`
- `MoveAsync`
- `DeleteAsync`
- `ExtractTextAsync`

`IProposalService` 能力：

- `ListProposalsAsync`
- `CreateProposalAsync`
- `GenerateProposalAsync`
- `UpdateProposalAsync`
- `ConfirmProposalAsync`
- `ConvertToRequirementsAsync`

### 5.3 权限校验

复用现有项目参与人逻辑：

- 只读操作：项目参与人可访问。
- 上传、重命名、移动：项目经理、产品经理、架构师、超级管理员。
- 删除：项目经理、架构师、超级管理员。
- 提案转需求：项目经理、产品经理、超级管理员。

所有权限拒绝需要返回明确错误，写入安全审计时不记录文件物理路径。

## 6. 管理端页面设计

### 6.1 项目管理入口

项目管理卡片保持现有紧凑卡片模式，在项目详情抽屉中增加 `项目材料` 标签页或操作入口。

推荐第一版：

- 项目详情抽屉增加 `项目材料` tab。
- tab 内展示材料文件管理区。
- 如果材料管理交互变复杂，再增加隐藏详情路由 `/sprint/projects/:projectId/materials` 作为全屏页。

### 6.2 项目材料页面结构

按管理端列表规范组织：

1. 顶部标题和说明。
2. 筛选区。
3. 文件列表工具栏。
4. 文件表格。
5. 分页。

筛选区：

- 当前项目。
- 关键词。
- 文件类型。
- 分类。
- 上传人。
- 创建时间。

工具栏：

- 左侧展示当前目录和面包屑。
- 右侧按钮顺序：`上传`、`新建文件夹`、`刷新`。
- 刷新使用刷新图标。

表格列：

- 序号。
- 名称。
- 类型。
- 大小。
- 分类。
- 标签。
- 上传人。
- 上传时间。
- 抽取状态。
- 操作。

行操作：

- 文件夹：`打开`、`重命名`、`移动`、`删除`。
- 文件：`下载`、`详情`、`重命名`、`移动`、`删除`。
- 每个行操作需要图标和文字。

### 6.3 上传弹窗

上传使用 Dialog 或 Drawer，不在列表页主体铺表单。

字段：

- 上传文件。
- 目标目录。
- 分类。
- 标签。
- 说明。

交互：

- 支持拖拽或点击选择。
- 上传前展示文件名和大小。
- 上传成功后关闭弹窗并刷新列表。
- 上传失败展示服务端错误。

### 6.4 提案管理页面

后续新增 `敏捷研发 / 提案管理` 菜单。

页面结构：

- 左侧项目上下文。
- 右侧提案列表。
- 筛选：状态、关键词、创建人、创建时间。
- 工具栏：新增提案、从材料生成、刷新。
- 表格：标题、项目、状态、来源材料数量、创建人、更新时间、操作。

提案详情建议使用抽屉：

- 基础信息。
- 来源材料。
- AI 对话。
- 提案正文。
- 转需求记录。

### 6.5 从材料生成提案

入口可以在两个位置：

- 项目材料列表勾选材料后点击 `生成提案`。
- 提案管理点击 `从材料生成` 后选择项目材料。

流程：

```text
选择项目
  -> 选择材料
  -> 填写提案标题和生成指令
  -> 创建提案草稿
  -> AI 生成提案正文
  -> 用户编辑和确认
  -> 转需求
```

## 7. AI 上下文设计

### 7.1 材料上下文组装

提案生成时按优先级组装：

1. 用户输入的生成指令。
2. 项目信息。
3. 选中材料的文件名、分类、标签和摘要。
4. 可抽取文本的关键片段。
5. 现有需求或缺陷摘要，后续可选。

上下文限制：

- 不把二进制文件直接塞进 prompt。
- 大文件只使用摘要和切片。
- 每次生成保存材料哈希，保证可追溯。

### 7.2 提案生成提示词边界

AI 只生成提案草稿，不直接创建需求。

提示词需要强调：

- 输出结构化提案。
- 标出不确定信息。
- 标出需要人工确认的前提。
- 给出可转需求的候选条目。
- 不编造不存在的项目事实。

## 8. 提案转需求设计

转换策略：

- 单提案可转一条需求。
- 单提案也可拆成多条需求。
- 每条需求要有标题、正文、验收标准、优先级和来源提案。

转换接口输入：

```json
{
  "proposalId": "proposal-1",
  "requirements": [
    {
      "title": "需求标题",
      "description": "需求正文",
      "acceptanceCriteria": ["验收标准"],
      "priority": 2
    }
  ],
  "submitForReview": false
}
```

处理逻辑：

- 校验提案属于项目。
- 校验当前用户可转需求。
- 创建 `SprintRequirement`。
- 写入 `SprintProposalRequirement`。
- 写入需求事件。
- 如果 `submitForReview=true`，复用现有提交评审逻辑，不能绕过评审人校验。

## 10. 测试策略

后端测试：

- 上传保存文件和数据库元数据。
- 路径穿越被拒绝。
- 非项目成员访问被拒绝。
- 删除后下载被拒绝。
- 文件夹非法移动被拒绝。
- 提案不能引用跨项目材料。
- 提案转需求保留来源关系。

前端测试：

- 项目材料列表渲染。
- 查询、重置、分页、刷新。
- 上传弹窗。
- 行操作按钮状态。
- 材料选择生成提案。

集成验证：

- 本地 API 上传文件后，磁盘目录存在文件。
- 重启 API 后材料列表仍可查询和下载。
- Docker 部署时挂载目录后文件不会被发布覆盖。
